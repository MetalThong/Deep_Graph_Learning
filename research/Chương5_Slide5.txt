1 Lecture Overview
This lecture is designed as the next stage after students have studied machine learning and
deep learning applications such as:
• diabetes prediction;
• MNIST image classification;
• house-price prediction;
• stock-price prediction;
• gold-price prediction;
• CNN-based image classification;
• RNN and LSTM sequence modelling.
The central transition in this lecture is:
From learning patterns from data to developing intelligent systems
that can use knowledge.
The objective is not simply to teach students how to call an LLM. The objective is
to understand the architecture of a modern knowledge-based intelligent system and then
implement a small domain-specific conversational application.
1.1 Learning Outcomes
After completing this lecture, students should be able to:
1. explain why prediction models alone are not complete intelligent systems;
2. distinguish structured and unstructured knowledge;
3. construct a simple Knowledge Graph;
4. represent knowledge using entities and relations;
5. understand document chunking;
6. understand embeddings;
7. implement semantic retrieval;
8. explain Retrieval-Augmented Generation (RAG);
9. implement a basic RAG system;
10. combine Knowledge Graph retrieval with vector retrieval;
11. evaluate retrieval quality;
12. evaluate answer quality;
13. build a simple conversational interface;
14. deploy a small domain-specific intelligent chatbot.

2.1 Prediction Versus Knowledge
Consider the following questions:
What is diabetes?
Why does a CNN work well for images?
What is the difference between CNN and RNN?
What is an LSTM?
What is RAG?
Why does RAG need retrieval?
What is a Knowledge Graph?
A classifier or regressor does not directly answer these questions.
The problem has changed.
Instead of
x→y,
we now have
Question→Knowledge→Reasoning→Answer.

A modern intelligent application can be represented as
Data→Representation→Knowledge→Retrieval→Model→Decision or Conversation
The machine-learning model is therefore only one component.

3 Knowledge Representation
Knowledge can be represented in several different forms.
3.1 Structured Knowledge
A conventional relational database stores information in tables.
A Knowledge Graph stores entities and their relationships.
For example:
(CNN,is-a,Deep Learning Model)
(CNN,used-for,Image Classification)
(MNIST,used-by,CNN)
A Knowledge Graph therefore explicitly represents relationships.
3.2 Unstructured Knowledge
Much useful knowledge is stored in documents:
• lecture notes;
• PDF files;
• textbooks;
• laboratory instructions;
• web pages;
• technical reports;
• source code documentation.
For example:
Convolutional neural networks are widely used for image classification because
convolutional layers can learn local spatial patterns.
This sentence contains knowledge.
However, the relationship between
CNN
and
Image Classification
is not explicitly represented as a graph edge.

3.3 Why We Need Both
A Knowledge Graph is useful for explicit relationships:
CNN→used-for→Image Classification.
Documents are useful for detailed explanations.
Therefore a practical intelligent system may combine:
Knowledge Graph+Documents
This combination becomes particularly useful when building domain-specific assistants.

6 Embeddings and Semantic Representation
Keyword search mainly compares words.
Semantic retrieval compares representations of meaning.
An embedding model is a function
f :T →Rd,
whereT is the space of text andd is the embedding dimension.
For a sentence,
f (CNN classifies images) = [ x1, x2, . . . , xd].
The resulting vector is called an embedding.
6.1 Cosine Similarity
For two vectorsx and y,
sim(x, y) = xT y
∥x∥2∥y∥2
.
If the vectors are normalized,
∥x∥2 =∥y∥2 = 1,
then
sim(x, y) = xT y.
The retrieval problem becomes:
q = f (query),
di = f (documenti),
and
i⋆ = arg max
i
qT di.

18 Hallucination and Grounding
Large language models can generate fluent but unsupported information.
Without retrieval:
Question→LLM→Plausible Answer.
With RAG:
Question→Evidence→LLM→Grounded Answer.
However:
RAG reduces hallucination but does not guarantee zero hallucination.
18.1 Three Important Failure Modes
18.1.1 Retrieval Failure
The correct information exists, but the retriever does not find it.
Knowledge exists̸⇒Knowledge retrieved.
Possible causes:
• bad chunking;
• poor embedding model;
• ambiguous query;
• insufficient top-k;
• missing metadata.
18.1.2 Generation Failure
The correct evidence is retrieved, but the LLM misunderstands it.
18.1.3 Knowledge Gap
The answer does not exist in the knowledge base.
The system should then explicitly say:
The available knowledge base does not contain sufficient information to answer
this question.

23.1 Problem 1: Poor Retrieval

• embedding model is unsuitable;
